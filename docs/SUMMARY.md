# Summary

## Citable paragraph

In cloud-native authorization, a single security decision is often split
between a token verifier and a policy layer, and the two may decode the same
JWT payload with different JSON parsers. I ran a small pre-registered pilot to
measure how often such parsers disagree about the same bytes. It tested 12
parsers in isolation, at pinned versions: 2 policy-side (Open Policy Agent), 6
verifier-side JWT libraries and 4 general-purpose JSON decoders, across Go,
Python, Node.js and Rust. The 137 hand-built inputs covered duplicate and
case-variant keys, Unicode escapes, edge-case numbers, encoding and syntax
variants, and type confusion. Each token was validly signed, so only payload
parsing was under test. The question, corpus hashes, equality rules and 22
falsifiable predictions were committed publicly before any data was collected.
60 of the 66 parser pairs reported a different value for at least one of
`iss`, `sub`, `aud`, `exp` or `iat` on at least one input, and 61 of 66
disagreed on whether to accept at least one input. Every one of the 12
policy-side × verifier-side pairs showed both kinds of disagreement. The only
pairs with no value disagreement were those sharing an underlying decoder. Most
value disagreements came from number handling (exact integer, IEEE-754 double,
arbitrary-precision decimal, or truncation to an integer). Others came from
case-insensitive key matching in Go's `encoding/json` struct decoding and from
Unicode edge cases. Duplicate keys produced only accept-versus-reject
disagreement: every parser that accepted them took the last occurrence. These results describe
how isolated parsers handle crafted inputs. They do not show that any product
or deployment is affected. Parser differentials are an established
language-theoretic security topic, and the pilot's contribution is a small,
version-pinned, pre-registered measurement of them.
